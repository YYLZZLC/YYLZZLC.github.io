> 这是一个复合叙事。其中的公司、数字、事故都是虚构的，但每一个阶段的困境、决策和代价，都来自真实互联网系统里反复发生过的事。
> 我想讲的不是"架构应该长什么样"，而是**它是怎么一步步长成那样的**——以及每一步为什么要付什么代价。

---

## 0｜它开始于一台机器

2015 年春天，三个人的团队租了一台 4 核 8G 的云服务器，在上面跑一个叫「拾光」的东西。

它是一个生活方式社区：用户可以发图文、关注别人、收藏商品、跳转去第三方下单。

那时候它一天的访问量是两万多次，注册用户不到五万。整个技术栈朴素得不能再朴素：

- 一个 Java 应用，打成 war 包，扔进 Tomcat
- 一个 MySQL 5.6，和应用在同一台机器上
- 图片直接存服务器本地磁盘
- 用 `crontab` 跑定时任务
- 用 `tail -f` 看日志

代码是一份。改一行，重新打包，重启 Tomcat，二十秒的事。

**这个阶段最重要的一件事，不是它有多简陋，而是它有多"对"。**

三个人、几万用户、一天两万次访问——这个体量下，任何分布式设计都是纯粹的负担。你省下的不是成本，是**你本可以用来理解用户的时间**。当时他们没有做任何"为将来预留"的设计，这一点后来被证明是对的：那些预留，九成都会在你真正需要时发现是错的。

真正的麻烦，是从一次普通的周一早上开始的。

## 1｜第一道裂缝：读和写，差了六十倍

那年秋天，一篇讲露营装备的图文被一个大号转了出去。

一个晚上，访问量从两万涨到了四十万。

服务器没挂。但页面打开要七八秒，用户刷不出来就退出去了。运营在群里问："是不是挂了？"——它没挂，它只是慢得像挂了。

排查完，问题很清楚：**几乎所有请求都压在同一个 MySQL 上，而这个社区九成以上的访问是"看"，只有不到百分之二是"发"。**

一条图文详情页的请求，要查帖子、查作者、查作者的其他帖子、查是否已关注、查是否已收藏、查商品的库存展示——六次查询，五次是为了读。整个系统里，写的操作少得可怜，却和读操作抢同一个数据库连接池。

### 他们做的第一个改动：加缓存

做法很朴素：在应用和 MySQL 之间加一层 Redis，把图文详情、作者信息、热门列表塞进去。

效果立刻显现——详情页从七八秒回到两百毫秒。团队高兴了大概两个星期。

然后是第一个真正意义上的教训：**缓存不是免费的加速器，它是一个新的、你必须养着的数据源。**

他们遇到的第一个问题是"缓存里的帖子还是旧标题"：作者改了标题，页面三天没变。原因是更新的时候只写了库，忘了删缓存。第二周又反过来：他们加了"写完立刻删缓存"，结果高峰期删缓存的操作把 Redis 打满了。

第三个问题最要命。某天早上，一批热门帖子的缓存同时到期（因为它们是同一批预热进去的），所有请求一起穿透到数据库，MySQL 的连接数瞬间打满，整个站挂了四分钟。

后来他们才知道，这三件事在行业里都有名字：**缓存一致性、缓存击穿、缓存雪崩。**

### 这一阶段真正的决策

不是"要不要加缓存"——那个答案显然是加。真正的决策是两条：

**第一，接受"短暂的旧数据"。** 他们放弃了实时一致，把缓存 TTL 定成 5 分钟。这意味着作者改完标题，最长五分钟才会生效。产品经理起初不同意，直到有人问："用户真的在意一条帖子的标题晚五分钟更新吗？"——不在意。**这一条妥协，换来了后面所有高并发设计的空间。**

**第二，热点数据不允许"同时到期"。** 他们给 TTL 加了随机抖动，把缓存预热从"整点批量"改成了"分批错峰"。

### 代价，以及它引出的新问题

缓存挡住了读的压力，但有一个东西它挡不住：**写。**

发帖、关注、收藏、评论——这些操作必须落库。而那台机器上，MySQL 和应用还挤在一起，CPU 一高，数据库也一起慢。更麻烦的是，随着社区变大，"查我关注的人都发了什么"这类查询越来越重，开始拖慢整个库。

数据库，成了整个系统唯一的天花板。

## 2｜一台机器不够了，但两台机器不认识彼此

2016 年，他们把应用拆到了两台机器上，前面挂了一个 Nginx 做负载均衡。

结果上线第一天就出了个诡异的现象：**用户登录之后，刷新一下页面，又变回未登录。**

原因不难猜：登录信息（session）存在第一台机器的内存里，这次请求被 Nginx 分到第二台，第二台不认识这个 session。

这是很多人第一次真正理解"状态"这个词的时刻。

### 决策：让应用变成"没有记忆"的

两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 会话粘滞（sticky session） | Nginx 按 IP 或 cookie 把同一个用户固定打到同一台机器 | 最快，但一台机器挂了，上面的用户全部掉线；扩容时流量不均 |
| B. **把状态外置** | 登录态存 Redis，应用本身不存任何会话数据 | 多一次 Redis 调用，但任意一台机器都能接任意一个请求 |

他们选了 B。

这个决策的意义远超"解决登录失效"——它确立了一条后来一直在用的原则：**应用实例必须是可随时丢弃的。**

可随时丢弃，意味着可以随时加、随时减、随时杀掉重启。这一个属性，是后来所有弹性伸缩、滚动发布、故障转移的前提。**没有无状态化，就没有后面的一切。**

### 代价

- 每个请求多一次 Redis 读。这个开销在 QPS 低时无所谓，高了就是实打实的成本。
- 他们把会话粒度做小（只存 userId 和 token），避免大对象拖慢 Redis。

### 新问题

应用层现在能水平扩展了。数据库不行。

一台主库，撑起了全站。而且他们发现了一件更糟的事：**有人在做报表。** 运营每天要导出一份"昨日新增用户 + 发帖量 + 活跃度"的报表，这条查询会扫描几百万行，一跑就是四十秒，跑的时候全站变慢。

分析和交易，在抢同一个数据库。

## 3｜数据库成了唯一的天花板

2017 年，主库的 CPU 常年 70% 以上，慢查询日志一天几百条。

### 第一步：把读分出去

他们做了主从复制：一主两从，写走主库，读走从库。

配好之后，第二件麻烦事立刻来了：**用户发完帖子，刷新页面看不到自己的帖子。**

原因是最经典的"主从延迟"：写主库，立刻读从库，从库还没同步过来。

他们的解法不优雅但有效：**发帖之后的短时间内（比如 3 秒），这个用户的读请求强制走主库。** 业内叫"读己之写"。

代价是：这个方案需要在应用层维护一个"哪些用户刚写过"的标记，又要占内存，又要在多实例之间共享——于是又回到了 Redis。

**注意这个模式的重复出现**：每解决一个问题，就会引入一个新的、需要跨实例共享的状态。系统越复杂，共享状态越多，而这些共享状态本身又会成为新的瓶颈和故障点。这是一条贯穿始终的暗线。

### 第二步：分库分表

到了 2018 年，单表用户行为日志超过了 6 亿行。加索引也不管用了，因为索引本身大到内存装不下。

他们开始分库分表。

这个决策里有一个当时争议很大、后来被认为是最关键的选择：**分片键用什么。**

| 候选 | 优点 | 缺点 |
|---|---|---|
| 按时间分 | 天然冷热分离，老数据可以归档 | 热点全在当前时间片，等于没分 |
| 按用户 ID 取模 | 数据均匀 | 跨用户查询（比如"某话题下所有帖子"）要扫全部分片 |
| **按用户 ID 哈希 + 业务字段冗余** | 相同用户的数据永远在同一片，单用户查询快 | 跨用户查询必须走异步汇总 |

他们选了第三个。

代价很直接：**所有的"全局视角"查询都做不了了。**

排行榜、话题聚合、全站统计——这些原来一条 SQL 能出来的东西，现在要么走异步离线汇总，要么维护一张额外的汇总表。

这个选择的深远影响是：**从这一天起，系统的"实时"和"全局"变成了两个互斥的属性。** 你要实时，就只能看单片；你要全局，就得接受延迟。

### 新问题

数据能存了，读也能分散了。但下一个问题不是容量问题，是**时间问题**。

## 4｜大促那天，流量是平时的二十倍

2019 年双十一，「拾光」第一次做全场大促。

他们的准备是做足了容量估算的：按平时峰值的 5 倍扩容。结果开场三十秒，实际流量是平时的 20 倍。

不是服务器扛不住，是**链路太长**。一个下单请求要串行走七八个步骤：校验库存、算优惠、扣减、生成订单、发通知、加积分、更新推荐。每一步都要几十毫秒，串起来就是几百毫秒。并发一高，线程池瞬间打满，所有请求排队。

### 决策：把"必须现在做"和"可以等会做"分开

这是整个演进过程中，思维方式变化最大的一次。

他们把所有动作重新分了两类：

| 必须同步完成 | 可以异步完成 |
|---|---|
| 库存校验与扣减 | 发优惠券通知 |
| 订单创建 | 加积分、更新等级 |
| 支付确认 | 发短信、站内信 |
| | 更新推荐特征 |
| | 写行为日志 |

同步的部分只剩最关键的三步，其余全部扔进消息队列。

结果是：下单接口从几百毫秒降到几十毫秒，峰值扛住了。

### 代价：一致性从"天然"变成"要设计"

异步之后，第一个事故是：**用户下单成功，但积分没加。** 因为消费积分的服务重启了，消息丢了。

第二个事故更严重：**同一笔订单，积分加了两次。** 因为消息重投了，而消费端没有做幂等。

第三个事故最隐蔽：**优惠券超发。** 因为异步扣减有延迟窗口，两个请求同时看到了"还有一张"。

他们为此补了三样东西，这三样后来成了所有异步链路的标配：

1. **消息持久化 + 消费确认**——确保不丢
2. **幂等键**——每条消息带唯一业务 ID，消费端去重，确保不重
3. **预扣减 + 最终校准**——高竞争资源（优惠券、库存）先原子扣减，异步链路只做事后补偿

### 新问题

技术问题解决了一轮。但组织问题冒出来了。

## 5｜一百个人改同一份代码

2020 年，研发团队从 3 个人变成了 120 个人。

代码库还是那一份。

这带来的问题不是技术上的，而是**协作上的**：

- 任何一个人提交代码，都要等 CI 跑完 40 分钟的全量构建
- 一次发布，120 个人里只要有一个人代码有问题，全线回滚
- 两个人改了同一个文件，合并冲突要人工解半天
- 新来的工程师要花两周才能搞清这个 80 万行的单体里，一个功能到底在哪

**这时候拆分已经不是架构选择，而是组织刚需。**

### 决策：按业务边界拆

他们拆出了第一批服务：用户、内容、商品、交易、支付、消息、搜索、推荐。

拆分的原则当时很简单粗暴：**看代码目录，哪个包最大就拆哪个；看发布频率，哪个模块改得最勤就拆哪个。**

这个原则不优雅，但有效。因为它的依据是**真实的变更模式**，而不是教科书上的领域模型。

### 代价：一拆之后，什么都要重做

这是整个演进过程中，代价最大的一步。他们后来复盘，至少付出了四类成本：

**第一类：分布式事务。**
原来一个本地事务能保证的事（下单扣库存 + 生成订单），现在跨了两个服务。他们最终用的是"本地消息表 + 最终一致"，而不是强一致的分布式事务——因为强一致方案（如两阶段提交）在高峰期会锁住资源，吞吐掉得厉害。

代价是：**系统里出现了"中间状态"。** 订单已创建但库存还没扣，这个状态必须能对外表现成"处理中"，而且必须有补偿任务去兜。

**第二类：链路变长，排查变难。**
原来一个错误堆栈能看到全部。现在一个用户投诉"下单失败"，要跨 6 个服务翻 6 份日志——而且每份日志的时间戳还差几毫秒，你不知道该按哪个对齐。

**第三类：同一个能力被写了两遍。**
拆的时候没人管公共能力，结果"用户信息校验"在交易服务里写了一遍，在内容服务里又写了一遍，规则还不一样。

**第四类：运维成本翻倍。**
8 个服务，每个都要配监控、配日志、配告警、配发布流水线。

### 新问题

服务拆开了，但机器变成了几十台虚拟机，配置靠人写脚本，扩容靠运维手工开机器，发布靠半夜值守。

**机器的数量，开始拖住人的速度。**

## 6｜服务多了，机器碎了

2021 年，他们有 60 多个服务、300 多台虚拟机。

问题变成了：

- 每个服务申请机器要等运维排期，一个扩容需求等三天
- 机器利用率极不均匀：有的服务 CPU 10%，有的 90%，但都各自占着自己的机器
- 环境不一致："我这能跑啊" 成了口头禅
- 上线要改一堆配置文件，改错一个就事故

### 决策：容器化 + 编排

他们把服务打成镜像，跑在 Kubernetes 上。

这一步的真正价值不在于"用上了 K8s"，而在于三件具体的事：

**第一，扩缩容从"天"变成"分钟"。** 大促前把交易服务从 20 个实例拉到 200 个，十分钟完成。活动结束自动缩回去。

**第二，资源变成"池子"。** 所有服务共享一个机器池，按需分配，利用率从平均 15% 提到了 40% 多。

**第三，环境一致。** 镜像里包含了运行时的一切，"我这能跑"这个问题消失了。

### 代价

- **调度变得不可控**：实例被调度到哪台机器、和谁做邻居，你不再完全决定。一次噪声邻居（同一个机器上的另一个服务狂吃 IO）就可能让你的延迟翻倍。
- **诊断变难**：容器挂了，日志跟着没了。他们必须强制所有日志输出到统一收集，且容器退出前要保留现场。
- **优雅下线成了必修课**：滚动发布时，旧实例被 kill 的瞬间，正在处理的请求会失败。他们加了 preStop 钩子 + 健康检查摘流，才把这个错误率压下去。

### 新问题

到这里，系统的形态已经接近今天的样子了：几百个服务实例、容器编排、弹性伸缩。

但有一个问题从最开始就存在，只是现在被放大到了极致：**一个大促级别的故障，会顺着调用链，把所有服务一起拖下水。**

---

## 7｜故障不再是意外，而是常态

2022 年的一次事故，被他们内部称为"黑色四十分钟"。

起因很小：搜索服务的一个下游接口变慢（不是挂，是慢，从 20ms 变成 2s）。

后果是：
1. 搜索服务的线程池被占满
2. 搜索服务的调用方（首页、详情页、推荐）也开始排队
3. 这些调用方所在的服务线程池也被占满
4. 首页白屏，详情页打不开，推荐降级失败
5. 整个 App 有 40 分钟打不开

**一个慢接口，拖垮了整个系统。** 这件事让他们彻底理解了"雪崩"这个词——它不是比喻，是一条真实的传导路径。

### 决策：给每一条依赖都装上"保险丝"

他们做了四件事，这四件事后来成了所有服务的强制规范：

**第一，超时。** 每个下游调用必须有超时，且超时时间要小于上游的超时时间（否则等于没有超时）。这条听起来简单，但当时他们发现有一半的调用根本没有设超时，用的框架默认值是无限制。

**第二，熔断。** 当某个下游的错误率超过阈值，直接快速失败，不再调用。给下游恢复的时间，也保护自己不被拖死。

**第三，隔离。** 不同业务用不同的线程池（或信号量），一个业务的慢调用不会耗尽所有资源。首页和交易不能共用同一个池子——因为首页可以降级，交易不能。

**第四，限流。** 在最外层（网关）按接口限流，防止单一来源把系统打满。

### 代价：系统复杂度上了一个台阶

这四件事每一件都会引入新的决策点：

- 超时设多少？（设短了误杀，设长了传导）
- 熔断阈值多少？（太敏感会频繁误熔断）
- 降级返回什么？（返回空、返回旧数据、还是让用户看到"稍后再试"？）
- 限流按什么维度？（IP、用户、接口？限多少？）

**这些问题没有标准答案，只能按业务逐个决定。** 而且决定了之后要有文档，否则半年后没人记得为什么这个值是 300 而不是 500。

### 新问题

链路保护和隔离做完了。但有一个问题他们一直没解决，反而更严重了：**出了事，没人说得清是哪里出的。**

## 8｜出了事，但没人说得清哪里出错

上面那次"黑色四十分钟"，他们的定位用了 25 分钟，修复用了 15 分钟。

25 分钟里，六个人在六个终端上翻日志，靠时间戳对齐，靠猜。最后是一个工程师想起来"搜索服务最近在灰度一个新接口"，才缩小到范围。

### 决策：把"看不见"变成"看得见"

他们建了三样东西，业内叫可观测性三支柱：

| 支柱 | 解决什么问题 | 他们用的 |
|---|---|---|
| 指标 Metrics | 现在系统整体健康吗 | Prometheus + Grafana |
| 链路 Traces | 这一个慢请求，慢在哪一段 | SkyWalking |
| 日志 Logs | 这一段代码当时发生了什么 | ELK |

其中对他们帮助最大的，是**链路追踪**。

原理不复杂：请求进来时生成一个 traceId，每经过一个服务、每次调用一个下游，都记一段 span（开始时间、耗时、状态）。一次请求结束后，你看到的是一棵调用树，能直接看出"这 800ms 里有 700ms 花在搜索服务的某个下游调用上"。

装上之后，同样的问题定位时间从 25 分钟变成了 3 分钟。

### 代价：数据量本身成了问题

链路追踪的数据量是惊人的。5000 个实例、每秒几万请求、每个请求十几个 span——一天下来是千亿级的记录。

他们的做法是**采样**：正常请求按 1% 采样，出错请求全采，慢请求全采。这个策略的关键在于：**你必须在"出事的时候"有完整数据，所以"只采样正常的、全留下异常的"是唯一可行的方式。**

代价是：你不能用链路数据做精确的业务统计，因为它不是全量的。这个边界必须提前和业务方说清楚，否则一定会有人拿采样数据算 GMV。

### 到这里，系统的形态

2023 年，系统大概长这样：

- 200+ 个微服务，峰值 5000+ 个运行实例
- 全部跑在容器编排平台上，按负载自动伸缩
- 数据层：分库分表的关系库 + 缓存 + 搜索引擎 + 消息队列
- 全链路有超时、熔断、隔离、限流
- 有完整的指标 / 链路 / 日志体系

看起来，该有的都有了。

但还是有一件事，一直悬在头上。

## 9｜一个机房装不下了

2024 年，单机房容量到顶了。

不是机器不够，是**单机房的电力、网络、故障域都到极限了**。而且有一个更根本的问题：机房整体故障时，业务会停多久？

答案是：会停很久。因为所有东西都在一个机房里。

### 决策：单元化

这一步是整个演进里最难的，也是唯一一个必须改数据模型的。

思路是：把用户按 ID 切成若干"单元"，每个单元是一个完整的、可以独立运行的小系统（包含自己的应用实例、自己的数据库分片、自己的缓存）。流量进来时，在最前面按用户 ID 路由到对应单元。

这样一来：
- 一个单元故障，只影响这个单元的用户（比如 10%）
- 扩容可以在单元内做，也可以加新单元
- 机房级故障时，可以把一个单元整体切到另一个机房

### 代价：所有"跨用户"的操作都变难了

这是最痛的地方。

- 两个不同单元的用户互相关注，数据怎么同步？
- 全站排行榜怎么做？
- 一笔交易涉及买卖双方在不同单元，事务怎么处理？

他们的解法是：**核心交易数据留在单元内，全局数据用异步汇总。**

也就是说，架构上明确承认了一件事：**不是所有数据都能实时全局一致。** 你必须在设计阶段就决定，哪些数据必须强一致（交易），哪些可以最终一致（社交关系、排行榜、统计）。

这个决定不是技术选择，是**业务选择**——需要产品、运营、技术一起定。

## 10｜回头看：它是怎么长成这样的

十年，从一台机器到 5000 个实例。

如果只看最后的样子，会觉得这是一套精心设计过的架构。但它从来不是被设计出来的——**它是被问题一步步逼出来的。**

我把这条路径上的每一次变迁整理一下，你会发现一个规律：

| 阶段 | 撑不住的地方 | 做了什么 | 付出什么 | 引出什么新问题 |
|---|---|---|---|---|
| 单体 | 读多写少，全压一个库 | 加缓存 | 一致性妥协、缓存三坑 | 写入成为瓶颈 |
| 多实例 | 会话不一致 | 无状态化 | 每次多一次 Redis 调用 | 数据库仍是单点 |
| 读写分离 | 主库压力 + 报表干扰 | 主从 + 读己之写 | 需要跨实例共享状态 | 数据量到顶 |
| 分库分表 | 单表过大 | 按用户分片 | 全局查询做不了 | 峰值扛不住 |
| 异步化 | 同步链路太长 | 消息队列削峰 | 最终一致、丢重、超发 | 组织协作崩了 |
| 微服务 | 100 人改一份代码 | 按变更模式拆分 | 分布式事务、链路变长、重复建设 | 机器管理失控 |
| 容器化 | 300 台机器靠手工 | K8s + 弹性 | 调度不可控、诊断变难 | 故障传导放大 |
| 稳定性治理 | 一个慢接口拖垮全局 | 超时/熔断/隔离/限流 | 复杂度上升、需逐个调参 | 定位不了问题 |
| 可观测性 | 25 分钟找不到根因 | Metrics/Traces/Logs | 数据量爆炸、必须采样 | 单机房到顶 |
| 单元化 | 机房容量与容灾 | 按用户切单元 | 跨单元一致性只能最终一致 | —— |

### 三个我看到的东西

**第一，每一个"解决方案"都精确地变成了下一个问题的来源。**

缓存带来了不一致，异步带来了重复和丢失，拆分带来了分布式事务，容器化带来了调度不可控。这不是失败的证据，这是演进的本质——**你不可能既获得一个能力，又不承担它带来的新约束。**

所以看一个架构方案时，真正该问的不是"它解决了什么"，而是"它把什么问题推迟到什么时候、以什么形式爆发"。

**第二，所有架构决策最终都会撞上组织。**

120 个人改一份代码，才逼出了微服务；一次事故要六个人翻日志才逼出了可观测性；一个慢接口拖垮全站才逼出了熔断。**技术架构的形状，和组织的形状是同一件事的两个面。**

**第三，也是最反直觉的一点：文中的很多决策，今天可能是错的。**

2015 年不做分布式是对的，因为三个人的团队维护不了。2020 年必须拆，因为 120 个人改不来。2024 年要做单元化，因为单机房到顶了。

**这些决策没有一个是"永远正确"的。它们都是"在当时的约束下最优"。**

所以我一直觉得，判断一个架构师的水平，不是看他知不知道这些方案，而是看两件事：

1. 他能不能说清**每个方案放弃了什么**；
2. 他能不能判断**现在这个阶段，该用哪一个**。

这两件事都没法从书上学，只能从一个一个真实的坑里长出来。
