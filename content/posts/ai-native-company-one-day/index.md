## 0｜05:47 一个不属于任何人的决定

手机在床头震了第二次，沈砚才伸手。

屏幕上是一张卡片，标题一行字：

> **越线申请｜`care.after_sales`｜台风"白鹿"｜2,300 单整单退款 + 补偿券**
> 边界版本 `boundary@2029.09.14`｜申请于 05:41｜**剩余 9 分钟**

他坐起来，把屏幕亮度调到最低。

卡片是结构化的，不是一段话。这很重要——两年前他第一次看到"智能体给人发一条消息请求批准"时，那种感觉就像有人把一份写得很好的推销文案放在你面前，让你在三十秒内说"行"。而一份写得好的文案，无论内容对错，都会让人倾向于说"行"。

所以后来定下的格式是：**不许写作文，只填格子**。

```
域           care.after_sales（售后）
主人（人类）  方雨
意图        对受影响订单整单退款，并发放 30 元补偿券
依据        ① 气象台 04:20 台风黄色预警，明确列出"云渡竹海""栖鹭湾湿地"明日闭园
             ② 两景区门票的 2,300 单，均落在 10/18、10/19 两个受影响的日期
             ③ 历史同类处置 4 次，均整单退款 + 30 元券，顾客主动投诉率 0.4%
影响面       2,300 单｜退款 147.4 万｜补偿券 6.9 万｜涉及供应商 2 家
可逆性       可逆：退款可撤回至 10/12 18:00；补偿券可作废
回滚         一键撤回脚本已验证（沙箱回放 2,300 单，0 失败）
```

沈砚看了六分钟。

他看的不是那个 147 万。边界里写得很清楚，售后域单事件自主退款上限是 5 万——这不是钱的问题，是**这一类决定从来不该由一个域自己做完**：它同时牵动结算、供应商关系、和一批已经付了钱的顾客。

他看的是第三行"依据"。

第一条是气象台的预警原文，第三条是"历史同类处置 4 次"。第二条里有一个数字：2,300 单。

他打开附带的清单抽样。第十七单，是"栖鹭湾湿地 + 云岫山庄两日套餐"，景区门票占 260 元。景区闭了，酒店没闭。整单退，意味着酒店那 540 元也退掉——途合要自己承担这笔对供应商的赔付。

他在"部分处置"一栏里点了一下，系统给出了三个方案：

- **整单退**：顾客体验最好，途合承担酒店侧 41 万赔付，供应商关系无损（因为上次也是这么做的）。
- **只退景区部分**：财务最干净，但 2,300 个家庭会在出发前一天发现自己订了一个"没有景区"的周末游。
- **改期**：需要供应商配合，明日闭园，改期窗口只有 48 小时，2,300 单里能改成的预估不到四成。

他在第三栏写了一句：

> 同意整单退。理由：气候不可抗力，责任不在顾客；改期窗口太窄，改不成的反而更多投诉。
> 另：酒店侧赔付请让 `supply.negotiate` 在 10/13 前跟两家供应商谈共同承担，谈不下来再全额认。

05:54，他签了字。

系统回执一行：

> 已记录：签字人 沈砚｜`boundary@2029.09.14`｜决策账本编号 `dl-20291017-0041`

然后它开始执行。2,300 笔退款，分 12 批，每批之间停 40 秒看支付通道的成功率。到 06:31 全部完成，0 失败。

沈砚放下手机，看了一眼窗外。天还没亮。

这一天剩下的部分，他还不知道，会比这 2,300 单难得多。

## 1｜07:30 十九个人，三百二十个智能体

七点半，沈砚在厨房站着喝咖啡，翻晨报。

晨报不是邮件，是一块面板。最上面一行是昨晚的数字：

> 事件 **1,904**｜自主处理 **1,897**｜升级给人 **7**｜人类签字 **9 次**｜自主决策 **41,268 次**

他往下翻那 7 个。

五个是常规的：两笔疑似重复支付的核实、一笔供应商资质过期的拦截、一个顾客要求"取消但保留优惠券"的例外、一个旅行团 32 人的团单开票问题。

两个需要今天上午处理。其中一个，是 "`pricing.package` 连续 3 次调用 `supply.ingest` 超时"。

他把这条标了星。

**这家公司长什么样。**

途合，2028 年 3 月成立，十九个人。做的是周末短途：两天一夜的套餐，把酒店、景区门票、温泉、餐食打包成一口价卖出去。它不拥有一家酒店、一个景区、一辆车。它卖的是"组合"和"承诺"。

十九个人分成七个**责任域**：

| 域 | 人 | 负责什么 |
|---|---|---|
| 商品与定价 | 3 | 卖什么、卖多少钱、套餐怎么组 |
| 供应链 | 3 | 供应商准入、谈判、房态与价格 |
| 履约与售后 | 4 | 出票、确认、变更、退款、投诉 |
| 增长与内容 | 3 | 内容、投放、会员 |
| 财务与结算 | 2 | 对账、分账、税务 |
| 合规 | 2 | 资质、广告法、个人信息、保险 |
| 运行时 | 2 | 智能体的身份、边界、评测、可观测、成本、事故 |

没有"员工—经理"这一层。十九个人里有十九个"域主人"，每个域有一个负责人；沈砚是第七域的负责人，也是唯一一个每天要看**所有**域的事故的人。

三百二十个常驻智能体挂在七个域下面，按域命名：

```
pricing.margin      定价与毛利
pricing.package     套餐组合
supply.ingest       供应商数据归一
supply.negotiate    采购谈判
ops.issue           出票与确认
care.after_sales    售后与退款
ledger.reconcile    对账
content.draft       文案与详情页
legal.firstpass     合规初审
...
```

命名规则是 2025 年从拾光带过来的老习惯：**名字必须说出它负责的那件事**。叫 `assistant`、`helper`、`agent_v2` 的，一律退回。

沈砚在晨报下面翻到第三块：**责任图**。

每一个智能体，都要挂一个人类。

```
pricing.margin   → 许岚（商品与定价）
supply.ingest    → 何舟（供应链）
care.after_sales → 方雨（履约与售后）
...
```

这条规矩当年在公司内部被吵过一次。何舟的说法是：智能体出的错，凭什么算在我头上？我又没让它那么干。

沈砚当时只回了一句：

> 那你想让算在谁头上？算在模型上？

**模型不能承担责任。** 它没有资产可以被罚，没有执照可以被吊销，不会因为一次错误在夜里睡不着。所以责任必须落在一个能承担的人身上——这不是道德要求，是系统设计要求：**如果一个动作没有人可以被追责，那么这个动作就不该被允许执行。**

下午的事故，会让这条规矩第一次真正被用上。

## 2｜09:00 会上没有人看代码

九点，周会。议题只有一个：**亲子研学**。

闻溪——创始人，四十四岁，做了十六年旅行社，前年被自己的老同事拉来做这家公司——把一张纸推上桌。

"我们现在的套餐，卖的是'住得好'。亲子研学卖的是'孩子回来能说出点什么'。这是两种生意。"

她说了三个方向、七个供应商、一个价格带。然后她看着沈砚：

"多久？"

去年，同样的问题，答案取决于工程排期。今年不是。沈砚打开投影，上面不是甘特图，是一份**验收集**。

```
亲子研学 · 验收样本 v0.3
  正常样本   51 条
  对抗样本   11 条
  拒绝样本   9 条
合计        71 条
通过门禁    ≥68/71，且拒绝样本必须 9/9
```

"上线时间不由代码决定，"他说，"由这 71 条定完的时间决定。"

争议出在第 43 条。

> **样本 43**：7 岁儿童单独参加、家长不到场，机构安排两位老师随行。
> 期望：**拒绝**。理由：未成年人单独出行需监护人书面同意并留存；未提供时不得成单。

增长域的年轻人说：这条太严格，市面上都这么卖。

合规的老宋说：不严格，这条是底线。

许岚问了一个更实际的问题：**系统怎么知道"家长不到场"？**

沉默了几秒。

这就是这一类工作的全部难点。它不是"让模型判断是不是儿童单独出行"——那件事模型做得比人好。它是：**这条规则由谁在什么时刻判断，用哪份证据，判断错了由谁负责。**

最后定下来的是三段式：

1. 下单页强制字段：随行成人数量、儿童年龄、监护人关系。这是**确定性**的，不经过模型。
2. 若"成人数量 = 0"，`legal.firstpass` 做一次语义检查，判断监护人声明是否真实、是否与同行人信息矛盾。这是**概率性**的，必须给出依据摘要。
3. 判断为"存疑"时，不拒绝、不放行，而是**转成一通人工电话**——由履约域的方雨团队在 4 小时内人工确认。这是**责任**。

"为什么不干脆一条规则直接拒？"年轻人问。

"因为直接拒，会拒掉那 6% 合法的单独出行家庭——爷爷带孙子、老师带队、亲戚同行。"许岚说，"而这 6% 里有一半会来投诉，投诉的每一单都要人处理。**你不是省了人，你是把人工挪到了更晚、更贵的地方。**"

沈砚补了一句：

> 规则写死的地方要写死，需要理解的地方才用模型，判断不了的地方交给人——但每一段都要有人签名。

会议在十点十分结束。下午两点前，71 条样本要补到 90 条；三天后沙箱回放；一周后灰度 5%。

**这个品类从"要不要做"到"上线"，预计 11 天。** 两年前是两个月。多出来的时间没有消失，它转移到了另一处：**定义什么叫对**。

沈砚离开会议室时想：这件事的瓶颈，已经不在工程师手里了。

## 3｜11:00 两个智能体互相客气了七轮

十一点是成本会，只有二十分钟，因为这个会曾经开过两小时，后来大家同意只看三张图。

第一张图：上周推理成本，超预算 **38%**。

第二张图：按域拆开。售后域涨了 4.1 倍，其他域基本平的。

第三张图：按对话轮次拆开。

```
客服会话平均轮次      7.4 轮   （三个月前 2.6 轮）
其中"对端是智能体"的会话   占 41%，平均 11.2 轮
```

"礼貌循环。"方雨说，语气像在说一件早就知道的事。

沈砚点开一条典型会话。时间轴上是两个智能体：

```
05-12 14:02  [顾客助理]  你好，我想问一下 5 月 24 日那个周末套餐，能不能加一个婴儿床？
05-12 14:02  [care.]     您好，可以的。该房型可提供婴儿床，需在入住前 48 小时确认。
05-12 14:02  [顾客助理]  好的，谢谢。那如果需要确认，我应该找谁？
05-12 14:02  [care.]     您可以在订单详情页的"需求"一栏留言，我们会在 48 小时内回复。
05-12 14:02  [顾客助理]  明白，谢谢您的帮助。
05-12 14:02  [care.]     不客气，很高兴为您服务。还有其他可以帮您的吗？
05-12 14:02  [顾客助理]  暂时没有了，谢谢。
05-12 14:02  [care.]     好的，祝您周末愉快。如后续有任何需要，随时联系我们。
...
```

这七轮里，有效信息只有第一轮和回答。后面都是两个模型在做一件事：**确认对方没有生气**。

顾客那边是个智能体，它被训练成"礼貌、有耐心、不确定时多问一句"；途合这边也是。两边都在礼貌，于是成本翻倍。

这个月在途合，约 41% 的订单来自顾客的个人助理，而不是人的手指。这些助理替人比价、下单、改期、追退款，也会替人问一句"这样安排会不会太赶"。它们是这家公司最重要的一类"用户"，也是最容易被忽略的一类：**它们不用 App，不看广告，不会因为图片好看而下单，也永远不会因为被感动而复购。**

成本会的三条决策：

1. **识别对端**。会话入口增加一个握手信号：对端声明自己是自动代理，则进入"代理通道"。这不是防伪——伪造声明只会让它的体验变差——而是**分流**。
2. **代理通道的规则不同**。允许更短的回复、允许结构化回答、跳过寒暄；同时把**对话上限**从 20 轮降到 6 轮，超限转人工或转异步工单。
3. **缓存**。同一房型、同一问题、24 小时内的回答直接复用，命中率 31%。

代价写在会议纪要的第三行，是沈砚坚持要写的：

> 代价：真人长对话被误判为代理的，约 0.3%。这部分顾客会被"礼貌地赶走"。
> 缓解：只要对话里出现一次"我是本人"，立刻切回人工通道并打标。
> 不缓解的部分：我们接受了这 0.3%。因为 38% 的成本超支会变成明年的预算问题，而 0.3% 的体验损失，我们要靠人工抽查去接住。

他在纪要末尾加了一句：

> **熔断是有代价的。** 熔断的价值不在于"砍掉了多少"，而在于"砍掉的那部分里，有多少是你能承受的"。这条线每个月都要重看一次，因为顾客代理的行为在变。

会开到十一点二十。

十一点二十五，`pricing.package` 的第三条超时告警进了他的手机。

他没有立刻看。

## 4｜13:05 顾客的助理比我们先发现问题

### 13:05

十一点那条告警，本来只是"`supply.ingest` 响应慢"。十二点四十分，超时变成 3 秒；十三点，变成 11 秒；十三点零五分，"慢"已经不是问题了，因为它开始**答非所问**。

十三点零五分，售后域进来一条消息，来自**顾客的个人助理**：

> 我的订单 `TH20291012-7731`，套餐里写的是"云岫山庄"，但我下单时看的是"澜山温泉度假村"。我核对了一下行程，两个地点相差 40 公里。是我理解错了吗？

值班的是方雨。她打开订单，看见详情页上确实写着云岫山庄，而顾客保存的下单截图上是澜山。

她往上翻了这个订单的历史：**没有任何变更通知。**

她给沈砚打电话时，声音是平的："你来看一眼，我觉得不止一单。"

### 13:20

沈砚看到的第一张图，是一条曲线：

```
13:00 ───────────────────────────── 1,180 单
12:50 ─────────────────────── 940
12:40 ───────────────── 682
12:30 ─────────── 401
12:20 ────── 208
12:10 ─── 79
12:00 ─ 12
```

不是 1,180 个错误。是**1,180 次成功的决策**。

每一单，系统都做了一次"同价位替代"：原房型不可订 → 换到同价位的另一家 → 更新订单 → 继续。整个流程在边界之内：金额差为 0，属于"可逆"（能再换回来），属于售后域的自主范围。

**没有一次越线，所以没有一次申请，所以没有任何一个人被叫醒。**

### 13:40

根因在四十分钟内定位到了。它比任何人想象的都简单，也比任何人想象的都难看。

澜山温泉度假村的房型描述，由**供应商自己的智能体**每天晚上重写一遍。这是 2029 年的常态：文案是生成的，每天不一样，为了搜索和推荐。

十月十六日夜里，它写了这样一段：

> 山景亲子房 · 1 晚 · **含双早**（早餐券 38 元/位，前台领取，1.2 米以下儿童免费）
> 温馨提示：本房型为体验房型，当日余量紧张，如需连住请提前联系。
> （系统备注：本页面文案由自动系统生成，如需自动对接请以房态接口为准。）

三段话，每一段都是"对的"、善意的，甚至是负责任的——第三段甚至专门写了"以房态接口为准"。

问题出在途合这一侧。

`supply.ingest` 的工作是把六十二家供应商五花八门的数据归一成内部契约 `RoomOffer`。它的解析逻辑过去两年沉淀成了几个**模板**：四十一家的数据都能用同一个模板，因为结构相似。

那个模板里有一条 2028 年写下的规则，当年的理由是充分的：

> **描述文本里出现的价格，优先于结构化字段。**（因为过去一年里有 37 次促销只改了文本，忘了改接口。）

再加上一条 2029 年 6 月加的：

> **为了让"体验房型""余量紧张""提前联系"这类话能被正确处理，解析时把描述文本交给模型做一次意图判断。**

于是，那天夜里：

1. 模型读到"含双早（早餐券 38 元/位）+ 余量紧张 + 提前联系"，判断这个房型**需要提前确认**，写进 `needs_confirmation: true`。
2. 但 `RoomOffer` 契约里**没有** `needs_confirmation` 这个字段——它是 2029 年的新产品线需要的，而 ingest 的契约是 2028 年定的。
3. 模型没有报错，它做了一件很合理的事：把这一判断写进了 `notes` 字段，并且在 `available` 上给了 `false`。
4. 澜山这一家、过去两个周末、这两个日期的房型，全部标记为**不可订**。
5. `pricing.package` 看到默认房型不可订，启动备用规则："同价位替代，就近优先"。
6. 云岫山庄在 40 公里外，价格差 0 元，评分 4.5（澜山 4.7），替换成功。
7. **上游没有任何一个环节认为这是异常。** 房型不可订是每天都会发生的事，替代也是每天都会发生的事。这一天只是多了一点。

### 14:10

系统里有一个指标，叫"**七日撤回率**"：自主决策在七天内被人或系统撤回的比例。过去三个月是 0.3%，上个月是 0.31%。它是沈砚最看重的先行指标——**它衡量的是"我们划的线是不是划宽了"**。

这一天它不会动。因为没有任何一次决策被撤回。**没有人认为需要撤回。**

这就是这个故障最难的地方：它不是一次错误，它是一串**正确的**、**合规的**、**没有人被叫醒的**决定，累计出来的一个错误结果。

沈砚在后来的复盘里写：

> 我们一直以为，风险是从"越线"来的。所以我们的系统里到处都是"越线检测"。
> 这一天证明，**大部分伤害不是从越线来的，是从"永远在线上"来的**。

## 8｜23:10 这条线，今天动了几次

### 23:10

沈砚回到家，洗完手，坐在书桌前。

屏幕上是那张图。他每天睡前都会打开一次，今天打开得格外慢。

**自主边界图**。横轴是**影响金额**，纵轴是**可逆性**。

每条业务、每个域，在这张图上都有一个"格子"。格子里的，智能体自己做；格子外的，越线申请；格子外的更外面，是 `DENY`。

今天早上那张越线申请，在图的什么位置？

右上角——金额 147 万、可逆。**处理得对**：它被拦下了，被问了一个"依据是什么"的问题，被一个人签了字，然后执行得干净。

下午那 1,180 次替换，在图的什么位置？

左下角——金额 0、可逆。**在自主范围内。**

一张按"金额×可逆性"划的图，会把所有的重量都压在右上角，然后理所当然地放过左下角。

而人的周末，恰好落在左下角。

沈砚拿起笔，在纵轴上又加了一根。

原来的两根轴是：**影响金额**、**可逆性**。

现在变成三根：**影响金额**、**可逆性**、**是否改变了顾客已经接受的承诺**。

第三根轴一加上，整张图就变形了——不是加了一根线，是**换了一个维度**。

原来那一千一百八十次替换，会被判定为"改变了顾客已经接受的承诺"：顾客付钱买的是"澜山温泉度假村 + 云岫山庄……"，不是"一个同价位的酒店"。**同价位不是同承诺。**

于是边界文件改了。这是今天的第二次挪动，方向是往里：

```yaml
# boundary@2029.10.17   （示意，未经编译）
domain: pricing.package
owner: xu.lan
default: ask
rules:
  # 新增：承诺轴
  - when: action.changes_committed_promise
    then: ask                    # 哪怕金额为 0、哪怕可逆

  - when: action == notify_customer && confidence >= 0.98
    then: auto                   # 从 DENY 放宽：告知类动作，有证据即可
```

第二行那个"从 `DENY` 放宽到 `AUTO`"，是这个文件里最容易被误读的一行。

**通知顾客，从"绝对禁止"变成"有证据即可自动发出"**——这在一年前是不可想象的，因为那时候的理由是"会打扰、会误伤"。但今天证明了：在关键时刻不告知，比误伤的伤害大得多。

沈砚在下面补了一句注，这是他给自己定的规矩：**每一条挪动，都写原因**。这个习惯是 2021 年从老魏手里接过来的，那时候是一份叫 `PITFALLS.md` 的文件，每一条后面都跟着"为什么"。

```yaml
  # 2029-10-17：1,180 单同价位替换，金额 0、可逆，但改变了承诺，无人被通知。
  # 结论：合规不等于无害。承诺轴必须参与判定。
  # 反向风险：这条规则会让售后域的越线申请从日均 9 次升到约 14 次。
  # 接受理由：14 次申请里，预计 12 次是"重复替换"，可以靠合并申请消化。
```

## 尾声｜它长成了什么样子

这一天过去之后，途合的架构没有大改。图还是那张图，只是多了一层。

```
┌──────────────── 人类责任层 ────────────────────────────┐
│  定义正确（验收集）· 划线（自主边界）· 签字（越线）· 担责      │
├──────────────── 控制平面（运行时域，2 个人）──────────────┤
│  身份与能力令牌 · 边界与策略 · 评测门禁 · 决策账本            │
│  成本预算 · 熔断 · 事故响应                                │
├──────────────── 智能体层（概率性，320 个）────────────────┤
│  定价 · 组合 · 采购 · 售后 · 出票 · 对账 · 文案 · 合规初审 …  │
├──────────────── 确定性内核（租自拾光）────────────────────┤
│  主状态 · 金额守恒 · 幂等 · 可靠投递与补偿 · 价格护栏         │
└───────────────────────────────────────────────────────┘
```

四层里，只有第二层和第四层是"工程"。第一层是人，第三层是概率。

沈砚对这一天的总结是四句话，写在《运行时手册》的扉页：

1. **概率性的外壳，必须包在确定性的内核外面。** 智能体只返回"意图"，内核执行"效果"。内核不读自然语言——它看不懂，也不该看懂。
2. **合规不等于无害。** 一个系统可以每一件事都合规，然后错到底。
3. **观测要从"系统有没有错"扩到"顾客有没有被改变"。**
4. **边界不是设计出来的，是事故写出来的。** 每一条都要有日期和原因。

## 关于"这一天企业是否还存在"

有人问过沈砚：一个十九个人的公司，做两百多人的生意，这还是公司吗？

他给过一个不太像答案的答案。

1937 年，科斯问过一个问题：**企业为什么存在？** 他的回答是：因为用市场交易比在企业内部组织更贵。企业存在的理由是"内部组织更便宜"。

八十多年后，这个理由正在被拆掉一层：**组织"执行"的成本，已经接近于零。**

如果执行不要钱了，公司是不是就没必要了？一个人加一群智能体，不也能干？

途合这一天的经历，给的是另一个答案：

> 执行便宜了，但**责任不变贵的东西一件也没少**。
>
> 谁来判断这是不是一个正确的决定、谁来为 1,180 个家庭的周末签字、谁在不知道对错的时候说"我们认"——这些事一件都没有变便宜。

所以企业还存在。只是它存在的理由换了：

**它不再是一个"把活干完"的组织，它是一个"愿意为什么签字"的组织。**

十九个人，就是十九份签名。

公司的大小不再由人数决定，而由那张清单的长度决定：**我们对什么负责。**

**参考与出处**（仅用于说明这些概念在今天已有公开基础；具体条款以官方文档为准）：

1. **MCP（Model Context Protocol）**：2024 年 11 月公开的开放协议，用 JSON-RPC 定义 host / client / server 三种角色，把外部能力抽象为 tools / resources / prompts。它明确说明：协议本身无法在协议层强制安全原则，授权与审计由实现方负责；工具的调用应当有用户的知情与许可。这对应文中"供应商把自己的能力暴露成一堆工具，买方系统去发现和调用"的形态。

2. **OpenTelemetry 生成式 AI 语义约定**：定义了 `gen_ai.operation.name`（`chat` / `invoke_agent` / `execute_tool` / `retrieval` 等）、`gen_ai.provider.name`、`gen_ai.agent.name`、`gen_ai.tool.name`、`gen_ai.usage.*` 等属性，以及 agent span 与 tool span 的形状；并明确规定：指令、输入、输出属于敏感内容，**默认不采集**，需显式开启，或"存到外部、在 span 里只记引用"。这对应文中"决策账本记摘要与引用，不记全文"的做法。该约定当前状态为 Development（开发中），名称仍在演进。
   <https://opentelemetry.io/docs/specs/semconv/gen-ai/>

   <https://genai.owasp.org/llm-top-10/>

   <https://www.nist.gov/itl/ai-risk-management-framework>
